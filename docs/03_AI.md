# AI/ML Doc — Adaptive Learning Agent

Read `00_MASTER.md` first for scope and the data model. This is the AI dev's detailed spec — the largest and most novel part of the system.

## Responsibilities

1. Goal extraction from chat → structured profile fields
2. Digital Twin maintenance (skill vector, experience vector, behavior, state — all with confidence)
3. Skill gap engine
4. Hybrid recommendation engine
5. Prerequisite-aware path generator
6. Learning evidence + mastery estimation
7. Feedback/state analysis (pace, difficulty, emotion — with confidence)
8. Active questioning (ask only when uncertain, capped at 2/session)
9. Explanation generation
10. Mentor chat

Ship this as a Python module (`ai_service.py`) imported by the backend — simplest integration for a 3-person team. Functions should be pure where possible (data in, result out) so they're testable without the backend running.

## Internal interface

```python
def extract_goal(message: str, existing_profile: dict) -> dict:
    """Partial profile fields from a chat message."""

def chat_reply(message: str, profile: dict, history: list) -> dict:
    """Returns {reply, wants_clarifying_question: bool, question: str|None}."""

def recommend(profile: dict, top_k: int = 10) -> list[dict]:
    """Returns [{resource_id, score, reason_short}], ranked."""

def generate_path(profile: dict, recommendations: list[dict], previous_path: dict|None) -> dict:
    """Returns {milestones, change_summary} — change_summary is empty on first generation."""

def analyze_evidence(profile: dict, assessment_result: dict) -> dict:
    """Updates skill_vector/skill_confidence and behavior from a completion/quiz event."""

def analyze_feedback(text: str, context: dict) -> dict:
    """Returns {emotion, pace_signal, difficulty_signal, confidence_per_field}."""

def explain(profile: dict, resource_id: str, recommendations: list[dict]) -> str:
    """Grounded natural-language explanation."""
```

## 1. Digital Twin

Maintain as one JSON object per learner (see master doc §5). Update triggers:
- `extract_goal` → goal/constraints fields
- `analyze_evidence` → skill_vector, skill_confidence, behavior
- `analyze_feedback` → state (pace, difficulty_fit, emotion) + confidence

Never let a field silently jump to a confident value from one data point — use a simple exponential update (`new = old*0.6 + observed*0.4`) rather than overwriting, so noisy single events don't whipsaw the twin.

## 2. Skill gap engine

```
target_role → required_skills (lookup table you curate for the demo domain)
current skill_vector → gap = required - current, floored at 0
prerequisite filter → don't surface a gap whose prerequisite skill is also a gap (fix the prerequisite first)
→ prioritized_gaps (ordered list)
```
This can be a plain lookup table + simple arithmetic for the MVP — it does not need to be an ML model, and a transparent rule here makes the "explainability" story easier, not harder.

## 3. Hybrid recommendation engine

Implement these ranking dimensions for real (the full concept lists 9 — cut to these 4 for MVP, per the scope doc):
- **Skill-gap match** — does this resource address a prioritized gap?
- **Semantic similarity** — embed resource descriptions + the learner's goal/gap text, cosine similarity (this is where your existing v2/v3 TF-IDF+cosine pipeline is directly reusable — swap the vectorizer for sentence-transformer embeddings if time allows, TF-IDF is a fine fallback)
- **Prerequisite fit** — resource's prerequisites already satisfied by current skill_vector
- **Difficulty fit** — resource difficulty vs current skill level ± the learner's observed difficulty_fit state

Combine as a weighted sum, not an LLM call — keep ranking logic explicit and inspectable so you can show the actual numbers in the explanation. The LLM's job is to explain the ranking in words, not to be the ranking mechanism.

## 4. Path generator

- Build a DAG from `skill_prerequisites` restricted to the prioritized gaps
- Topological sort → group into milestones (2–3 skills each), attach top-ranked resource per skill
- On regeneration: keep completed milestones fixed; only re-sequence what's left
- Compute `change_summary` as a small diff against the previous version ("moved SQL earlier because you're ahead of pace on Python") — this powers the dashboard banner in `02_FRONTEND.md`

## 5. Learning evidence & mastery estimation

**Completion ≠ mastery — keep these as separate numbers everywhere, including internally.**

```
inputs: quiz_score, time_spent vs est_hours, completion status
mastery_estimate = weighted(quiz_score: 0.6, completion: 0.2, pace_penalty: 0.2)
```
Where `pace_penalty` reduces the estimate if `time_spent` was much higher than `est_hours` despite a high quiz score (possibly the quiz was easy or answers were looked up) — a simple heuristic is fine, don't over-engineer this for the MVP.

## 6. Feedback & state analysis

Prompt the LLM to return structured JSON, not prose:
```json
{ "emotion": "frustrated|confident|bored|overwhelmed|neutral",
  "pace_signal": "too_fast|too_slow|good|unclear",
  "difficulty_signal": "too_easy|too_hard|good|unclear",
  "confidence": 0.0 }
```
Also fold in behavioral signals cheaply, without needing NLP: long inactivity, quiz failure, time spent far outside `est_hours` — these can raise/lower confidence or bias the emotion estimate even with no free text at all.

## 7. Active questioning (capped)

```
for each field in [pace, difficulty_fit, emotion]:
    if confidence(field) < 0.5 and field materially affects the next recommendation:
        candidate_questions.append(specific_question_for(field))

if candidate_questions and questions_asked_session < 2:
    ask the single most impactful one
else:
    fall back to the current best estimate and say so in the explanation
    ("assuming moderate pace since we don't have enough signal yet")
```
Never ask a generic "how was it?" — the question must name the specific gap: *"You finished quickly but scored lower than expected — did the concepts feel hard, or was the quiz confusing?"* The backend enforces the session cap; this function should still know about it so it doesn't waste its "ask" on a low-impact field.

## 8. Replanning rules (make this a literal table, not vibes)

| Quiz score | Pace | Feedback signal | Action |
|---|---|---|---|
| ≥85% | faster than expected | "too easy" / bored | Compress/skip remediation, advance to harder resource for that skill |
| ≤50% | slower than expected | "struggling" / overwhelmed | Insert a remedial resource + guided practice before the next milestone |
| 50–85% | on pace | good/neutral | Keep path as-is |
| any | any | `unclear` on a field that would change the action | Trigger active questioning (see §7) before replanning |

Implement this as an explicit function, `decide_replan_action(evidence, state) -> action`, so it's inspectable and testable — this table *is* the "dynamic replanning" feature; don't let it live only inside an LLM prompt where you can't verify it does what the demo claims.

## 9. Explanation generation

Ground every explanation in the actual numbers from §3 and §2 — pass the LLM the specific gap addressed, the ranking score breakdown, and (if relevant) the replanning action taken, rather than letting it free-associate. Keep a template fallback for when the LLM call fails or is slow.

## 10. Data / setup for the demo domain

- `resource_catalog.json` — curated real resources for that domain
- `required_skills_by_role.json` — small lookup table for the skill-gap engine and the career-alignment %

## Evaluation approach (for the solution doc)

- Recommendation quality: a handful of curated personas, check top-k overlap with expected resources
- Path validity: assert no milestone requires a skill not yet unlocked by an earlier one
- Replanning correctness: unit test `decide_replan_action` against the table in §8 directly — this is your most testable "AI" claim, use that
- Explanation groundedness: spot-check explanations reference real numbers, not generic praise
